## 1. 背景・目的

### 解決する課題

日本の中小企業（従業員数50〜500名規模）は、IT運用を「情シス担当者」と呼ばれる1〜2名の個人に依存している。入退社時のアカウント管理、PC手配・セットアップ、SaaSの契約更新、障害対応、請求書処理といった業務が担当者のスキルと記憶に紐づいており、以下の構造的問題が生じている。

- **属人化リスク**：担当者の退職・病欠で業務が即停止する
- **スケールの壁**：社員数の増加にともない対応量が線形に増え、担当者が本来業務に集中できない
- **ガバナンスの空白**：誰がいつ何の権限を付与したか記録が残らない。法改正への対応も担当者任せ
- **コスト効率の低さ**：月額10〜50万円の外部IT支援費が発生するケースが多く、中小企業には重い負担

### 目指す状態

「管理」という人的負荷をAIとシステムに移管し、人間が本来業務に集中できる環境を実現する。具体的には以下の状態をゴールとする。

- 従業員は Slack / Teams の自然言語で申請するだけで、ITに関するあらゆる依頼が完了する
- Growtect 運用担当者は「AIが生成した提案の承認」のみを行い、実作業はシステムが自動実行する
- 全操作に監査ログが残り、コンプライアンス要件に自動対応できる

### ビジネスモデル

Growtect がMSP（マネージドサービスプロバイダー）として顧客のITを丸ごと運用代行する月額サブスクリプション型。顧客はツールを購入するのではなく、「IT管理が回っている状態」を購入する。

### 市場ポジション

ServiceNow・Freshservice などの既存ITSMは大企業向け・高コスト・自社IT部門が使う前提で設計されており、中小企業のアクセシビリティが低い。日本国内に「AIエージェントが中小企業のITを丸ごと自律運用するMSPプラットフォーム」という直接競合は2026年3月時点で存在しない（詳細は `inputs/competitive-analysis.md` 参照）。

## 2. スコープ（対象範囲）

### 対象ユーザー

| ユーザー種別 | 説明 |
|---|---|
| 従業員（エンドユーザー） | Slack / Teams 経由でITに関する依頼・問い合わせを送る一般社員 |
| Growtect 運用担当者（NOC） | Agent Console で承認キューを管理し、AIの提案を確認・承認する運用スタッフ |
| 顧客企業の承認者 | it_manager / department_head / ciso の権限で特定操作を承認する顧客側担当者 |

### 対象業務（IN スコープ）

- ITヘルプデスク（質問回答・アカウント申請・障害報告の受付と処理）
- IAM管理（Google Workspace / Microsoft 365 のアカウント作成・削除・権限変更）
- デバイス管理（DRESS CODE / Intune / Google Endpoint との連携）
- 調達管理（KDDI まとめてオフィスへの発注・追跡）
- 請求書処理（AP/Billing Ops：OCR → CMDB照合 → 担当者振り分け）
- インシデント管理・変更管理（ITIL 4 準拠）
- コスト管理（ライセンス最適化・IT支出ダッシュボード）

### 対象外（OUT スコープ）

- 一般的な経費精算・HR管理（SmartHR等との統合は将来検討）
- ERP（SAP・Oracle等）との直接連携
- ネットワーク機器の物理保守（WebOps Agentによる設定変更までで、物理作業は対象外）
- エンドユーザー向けデバイスの修理・交換（物理対応は対象外）

### 提供形態

- クラウドSaaS（マルチテナント型）
- エンドユーザー向けインターフェース：Slack / Teams（既存ツール上に重畳）
- Growtect運用担当者向け：Agent Console（Webアプリケーション）

## 3. 機能要件

### 3-1. Pulse Desk（従業員向けヘルプデスク）

従業員が Slack / Teams 上で自然言語により IT 関連の申請・問い合わせを行うと、Pulse Bot が一次対応し、必要に応じてエージェントが自動処理を行う。

**ユースケース一覧**

| ID | ユースケース | アクター | 概要 |
|---|---|---|---|
| UC-01 | アカウント作成依頼 | 従業員 → IAM Agent | 「山田さんのGoogleアカウントを作ってください」とSlackに送ると、Pulse Botが不足情報をヒアリングし、承認後にGoogle Workspace APIでアカウントを自動作成 |
| UC-02 | アカウント削除・退職処理 | 人事担当 → IAM Agent | 退職者の全SaaSアカウント一括無効化を申請。承認後に各サービスのAPIを順次呼び出し完結 |
| UC-03 | パスワードリセット支援 | 従業員 → Pulse Bot | パスワードリセット手順をRAGで検索・回答（実行不要の場合はRead操作のみで自動完結） |
| UC-04 | PC手配申請 | 従業員 → Procurement Agent | 「MacBook Air M3を1台注文してください」とSlackに送ると、発注内容・金額の承認後にKDDI APIで発注 |
| UC-05 | 障害報告とトラブルシューティング | 従業員 → InfraOps Agent | 「VPNに繋がらない」と報告すると、診断手順を提示。設定変更が必要な場合は承認フロー経由で実行 |
| UC-06 | SaaS ライセンス追加申請 | 部門長 → IAM Agent | 「Notionのシートを3つ追加してください」という申請を受け、CMDBのライセンス台帳と照合後、承認・実行 |
| UC-07 | 請求書の受領と処理 | メール → AP/Billing Ops | 請求書メールを受信するとOCRで金額・ベンダー・期限を抽出し、CMDBのベンダー情報と照合。担当者へ自動振り分け |
| UC-08 | レガシーシステムへのユーザー追加 | 運用担当 → WebOps Agent | APIのない旧勤怠管理システムに対し、ブラウザ自動化でユーザー追加。ドライランスクリーンショット確認後に実行 |

**チケット管理**

全ての依頼はチケットとして記録される。ステータス遷移は以下の通り。

```
受付 → 分析中 → 承認待ち → 承認済み → 実行中 → 完了
                                             ↘ 却下 / 否認 / エスカレーション
```

### 3-2. AIオーケストレーション

**エージェント構成**

オーケストレーターが依頼を受け取り、ITIL 4 規律に基づいて分類・ルーティングする。Read操作（情報取得・確認）は自律実行。Write操作（作成・変更・削除）は必ず承認ゲートを経由する。

| 分類 | エージェント | 主な責務 |
|---|---|---|
| 技術系 | IAM Agent | アカウント権限の意図解釈・承認判断・実行エージェントへのルーティング |
| 技術系 | Google Workspace Agent | Google Admin SDK 経由でのアカウント操作（実行専用） |
| 技術系 | M365 Agent | Microsoft Graph API 経由でのアカウント操作（実行専用） |
| 技術系 | InfraOps Agent | ネットワーク障害・端末不調の診断 |
| 技術系 | SystemOps Agent | SaaS設定確認・運用判断 |
| プロセス系 | Inc/Prob Agent | インシデント止血→RCA→恒久対策→ナレッジ化 |
| プロセス系 | Change/Release Agent | 変更影響範囲調査・手順作成・切り戻し管理 |
| バックオフィス系 | AP/Billing Ops Agent | 請求書OCR処理・CMDB照合・担当者振り分け |
| バックオフィス系 | Procurement/VendorOps Agent | 発注要件定義・社内承認・KDDI API連携 |
| バックオフィス系 | FinOps-lite Agent | IT支出ダッシュボード・未使用ライセンス検知 |
| バックオフィス系 | WebOps Agent | APIのないレガシーシステムのブラウザ自動化（最終手段） |
| ガバナンス系 | Policy Evaluation Agent | 全エージェントのアクション前にYAMLポリシーを評価するゲートウェイ |

### 3-3. Human-in-the-Loop（HITL）承認フロー

AIによる全Write操作は必ず人間の承認を経由する。

- **Slack Block Kit**：低リスク定型操作はSlack上で承認/却下ボタンを提示
- **Agent Console DeepLink**：中〜高リスク操作・WebOps操作はSlackにDeepLinkを通知し、Agent Console で承認
- 承認期限：24時間。期限切れは `it_manager` → `department_head` → `ciso` → Growtect NOC の順でエスカレーション

**HITL 段階的自動化ロードマップ**

| フェーズ | 適用範囲 | 自動承認の条件 |
|---|---|---|
| Phase 1〜2 | 全Write操作 HITL 必須 | なし（人間が全件承認） |
| Phase 3 | 低リスク定型操作の自動承認解禁 | LLM Evals スコア ≥ 95% かつ過去30日エラー率 0% |
| Phase 4 以降 | 中リスク操作の自動承認拡大 | CISO 書面承認 + 月次レビュー |

### 3-4. Agent Console（運用者向け管理画面）

Growtect 運用担当者が承認キューの管理・監査ログの確認・CMDB台帳の閲覧を行うWebアプリケーション。

| 画面 | 主な機能 |
|---|---|
| ダッシュボード | ロール別パーソナライズ表示。「今日自分が対応すべきこと」を最上部に集約 |
| 承認キュー | リスクバッジ（🟢低/🟡中/🔴高）・影響ユーザー数・操作対象サービスを表示したActionProposalカード |
| チケット詳細 | 状態遷移タイムライン・AIターン別ログ・会話サマリー |
| WebOps承認パネル | ドライランスクリーンショット表示・「確定実行」ボタン |
| 監査ログ | actor / event_type / ai_model フィルタ・CSVエクスポート |
| CMDB台帳 | デバイス・ユーザー・SaaSサービスの検索・閲覧（変更は承認ゲート経由） |

### 3-5. 台帳レイヤ（Single Source of Truth）

全エージェントの判断根拠として機能する3つの台帳をPostgreSQLで管理する。

| 台帳 | 管理対象 |
|---|---|
| CMDB（構成管理） | サービス・デバイス・依存関係・オーナー・契約更新日 |
| IAM（権限・アカウント管理） | 従業員・ロール・ライセンス数・例外承認ルール |
| Version（リリース台帳） | 環境別バージョン・リリース履歴・切り戻しポイント |

### 3-6. Policy-as-Code（業務ルール管理）

インボイス制度・電帳法などの法的要件を人間が読み書きできるYAMLとして管理する。法務・コンプライアンス担当者はYAMLの内容のみレビューすればよく、評価・実行は Policy Evaluation Agent が担当する。法改正時はYAMLを修正するだけで全エージェントの判断基準が即時更新される。

## 4. 非機能要件

### 4-1. サービスレベル目標

| 指標 | Phase 1〜2 | Phase 3 以降 |
|---|---|---|
| 稼働率（SLA） | 99.5%（月間 約3.6時間停止許容） | 99.9%（月間 約43分停止許容） |
| RTO（目標復旧時間） | 1時間以内 | 30分以内 |
| RPO（目標復旧時点） | 1時間以内 | 15分以内 |

### 4-2. セキュリティ・データ保護

- **多要素認証 + SSO**：全アクセスに MFA 必須。SAML/OIDC でシングルサインオン
- **JIT アクセス制御**：サービスアカウントトークンは操作完了後に即時 revoke。常時有効なトークンを持たせない
- **マルチテナントデータ分離**：PostgreSQL RLS（行レベルセキュリティ）でDBエンジンレベルの物理分離を強制
- **PII マスキング**：氏名・メールアドレス・電話番号はAI送信前にマスキング
- **データ国内保持**：全データを国内リージョン（Azure Japan East / AWS ap-northeast-1）に限定
- **暗号化**：SaaS APIトークンは Fernet（AES-128-CBC + HMAC-SHA256）で暗号化。鍵管理は Azure Key Vault / AWS KMS
- **テナント別シークレット分離**：`secrets/{tenant_id}/...` のパス構造で各顧客のシークレットを完全分離

### 4-3. 可用性・信頼性

- **マルチLLMフォールバック**：Azure OpenAI（Primary）障害時に AWS Bedrock（Claude Opus）へ自動切り替え
- **Celery 非同期処理**：Slack の3秒タイムアウト制約を非同期キューで回避
- **ドリフト検知**：デバイス管理システムを1時間ごとにポーリングし、台帳との差分を自動検知
- **バックアップ**：PostgreSQL WALアーカイブをクラウドストレージへリアルタイム転送。日次フルバックアップ + 7日間保持

### 4-4. 監査・コンプライアンス

- 「誰が・いつ・何を見て・何を承認・実行したか」を audit_logs テーブルに全記録（追記のみ・改ざん不可）
- AI分析ターン単位でモデル名・推論サマリーを保存
- 電帳法対応：電子取引データは S3 Object Lock / Azure Immutable Blob に保存
- インボイス制度対応：適格請求書発行事業者登録番号の確認を自動化

### 4-5. パフォーマンス

- Slack メンション受信から Celery タスク着手まで：3秒以内
- RLS 有効時の p95 レイテンシ：RLS なし時比 1.5 倍以内（同時 100 リクエスト）
- RAG 検索レスポンス：p95 で 2秒以内

## 5. 制約・前提条件

### 技術的制約

- Slack の Webhook タイムアウトが 3秒であるため、全AI推論は Celery で非同期化する
- Google Workspace / Microsoft 365 の OAuth 構造上、真の「動的スコープ発行」は実現困難なため、操作後即時 revoke 方式を採用する
- Claude Computer Use API（WebOps Agent に使用）はベータ版であり、本番運用前にエンタープライズ契約でのSLA確認が必要
- WebOps Agent（ブラウザ自動化）は対象 SaaS の UI 変更により予告なく停止するリスクがある（Brittleness リスク）

### 外部依存の前提条件

- LMIS（ユニリタ）の REST API 仕様が Phase 1 開始前に確定していること（P1 未解決事項）
- KDDIまとめてオフィスが発注APIを提供していること（未確認・Phase 2 開始前に確認必要）
- DRESS CODE が API を提供していること（未確認・提供なければ WebOps Agent で代替）

### 法的・コンプライアンス制約

- 電子帳簿保存法（2024年1月義務化）：電子取引データの受領日時記録と改ざん防止措置が必須
- インボイス制度（2023年10月施行）：仕入税額控除に適格請求書発行事業者登録番号の確認が必須
- 個人情報保護法：PII の AI 送信前マスキングと国内データ保持が必須
- Azure / AWS のエンタープライズ契約により、入力データが AI 学習に使用されないことを技術的・契約的に保証

### 運用上の前提条件

- Growtect NOC 担当者が承認キューを業務時間内（最低8時間）に確認できる体制が整っていること
- WebOps Agent の Write 操作には Growtect NOC 担当者のドライランスクリーンショット目視確認が必須
- Phase 1〜2 では全 Write 操作に人間の承認が必要であり、完全自律実行は Phase 3 以降に段階的に解禁する
